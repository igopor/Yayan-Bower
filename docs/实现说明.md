## 阶段 2 · 账号

### 2.1 没有"注册"这个动作

**做了什么**：只提供 `POST /api/auth/sms/login`，内部用 `prisma.user.upsert`——手机号不存在就建号，存在就登录。

**为什么**：手机号 + 验证码天然就是"注册即登录"。多做一个注册页，等于让小学生多填一次同样的手机号和验证码，还要多维护一套"手机号已存在"的判断和提示。

**如果被问"用户从哪来"**：第一次输入验证码成功的那一刻自动建号，`user.phone` 上有唯一索引，不会建出两个同号账号。

---

### 2.2 验证码存在进程内存，没入库也没用 Redis

**做了什么**：`server/src/lib/captcha.ts` 里一个 `Map<手机号, {code, expiresAt, attempts, sendTimes}>`。

**为什么**：
- 没装 Redis（第一阶段就砍掉了），为 5 分钟生命周期的数据单独建一张表不划算；
- 重启丢失的影响很小——只是需要重新点一次"获取验证码"，已登录用户的 JWT 仍然有效，不会被打断。

**弱点（这是本模块唯一会被追问的地方，要能主动说出来）**：
只适用于**单进程**。如果哪天用 `pm2 -i max` 开多实例，请求可能落到没有这个验证码的进程上，校验必然失败。那时必须换成 Redis 或数据库表。现在 `pm2` 是单实例，不构成问题。

---

### 2.3 短信是一个接口，不是一个调用

**做了什么**：`server/src/services/sms.ts` 定义 `SmsProvider { send(phone, code) }`，两个实现：`MockSmsProvider`（只打日志）、`AliyunSmsProvider`（空壳，抛错提示怎么补）。切换靠 `.env` 的 `SMS_PROVIDER`。

**为什么**：现在没有备案，申请不到短信签名。如果不做这层抽象，业务代码里会写死"调阿里云"，等备案下来要改所有调用点；现在只是加一个实现类，改一行环境变量。

**如果被问"没备案怎么演示"**：Mock 通道下验证码固定 `123456`，登录全流程（频控、过期、错误锁定）都能完整跑，只是不发真实短信。前端会显示一条黄底提示告知这是开发模式。

---

### 2.4 只有一个 JWT，没有 refresh token

**做了什么**：登录发一个 7 天有效的 JWT，前端存 `localStorage`，每次请求带 `Authorization`。

**为什么**：这是给小学生用的学习工具，没有支付、没有隐私数据。掉登录最坏的后果是重新收一次验证码。加 refresh 轮换要多一张表、两个接口、一套失效处理，换来的只是"更久不用重新登录"，和这个产品的形态不匹配。

**如果被问"token 泄露怎么办"**：7 天自动过期；服务端无状态，无法主动踢人——这是明确的取舍，不是遗漏。真要踢人时加一张黑名单表，改 `/auth/logout` 一处即可（接口已预留）。

---

### 2.5 登录不跳转页面 —— 这是本模块最值得讲的一个设计

**做了什么**：前端 `auth.requireLogin(): Promise<boolean>`。业务代码这样写：

```ts
if (!(await auth.requireLogin())) return   // 用户关掉了登录框，放弃这次操作
await apiPost('/favorites', { termId })    // 登录成功，接着做原来要做的事
```

**为什么**：未登录用户点"收藏"，如果跳转到 `/login` 页，页面会刷新——用户刚输入的搜索词、滚动位置、浏览到第几条，全部丢失，登录回来要重新找。小学生的反应是直接关掉网站。

实现上不跳转，而是原地弹一个登录层；登录成功的瞬间，之前 `await` 住的那些 Promise 全部 resolve，调用方从下一行继续执行。**用户感知到的只是"弹了个框，填完，收藏成功了"**。

**如果被问"和 redirect 参数有什么区别"**：redirect 只能恢复 URL，恢复不了页面状态（搜索词、滚动位置、已加载的列表）。用 Promise 续做，状态根本没丢过。

---

### 2.6 未登录返回的是 `code: 40100`，不是 HTTP 401

**做了什么**：`ApiError.unauthorized()` 默认 `httpStatus = 200`，错误信息放在响应体的业务码里。前端 axios 拦截器两种都判断。

**为什么**：全站统一 `{ code, data, message }` 结构，前端只有一条处理分支。混用 HTTP 状态码会让"业务失败"和"网络失败"两套逻辑纠缠在一起。

**弱点**：不符合 REST 惯例，用 Postman 或者别的客户端接的时候要注意看 body 而不是状态码。对内部使用的前后端一体的项目，一致性比惯例重要。

---

### 2.7 所有 async 路由都套了 `route()`

**做了什么**：`server/src/lib/http.ts` 里的 `route(fn)`，把 Promise rejection 转成 `next(err)`。

**为什么**：Express 4 不会自动捕获 async handler 抛出的错误。直接写 `app.get('/x', async (req, res) => { throw new Error() })`，请求会一直挂着不返回，控制台只有一条 unhandled rejection，排查时非常迷惑。

**这是最容易踩的坑，新增路由时别忘了包。** 同步路由不需要。

---

### 2.8 积分不存冗余字段，直接对流水求和

**做了什么**：`buildUserSummary()` 里 `point_record` 按 userId 求 `SUM(delta)`，今日积分按 `createdAt >= 今天0点 AND delta > 0` 求和。

**为什么**：如果 `user` 表再存一个 `total_points`，就必须保证"加分时同时更新两个地方"，一旦哪次漏了，总分和流水对不上。家长看到"我今天加了 6 分，总分没动"，整个产品的可信度就没了。求和是毫秒级操作，几十个用户完全不需要缓存。

---

### 2.9 测试覆盖了什么

`server/src/lib/captcha.test.ts`（8 个）+ `server/src/lib/jwt.test.ts`（6 个），共 14 个，`npm test` 跑。

覆盖的是**纯逻辑里最容易错的部分**：冷却期、一小时发送上限、5 分钟过期、错误次数锁定、验证码一次性、伪造 token、过期 token。

**没覆盖的**：HTTP 层。这一层目前靠手动走查（见下）。如果以后想补，加 `supertest` 是最快的路径。

## 阶段 3 · 积分内核

### 3.1 幂等靠数据库唯一索引，不靠"先查一下有没有"

**做了什么**：`point_record` 上有 `UNIQUE(user_id, biz_type, biz_id)`。`grant()` 里也做了前置查询，但那是**优化**，不是保障。

**为什么**：学生连点两下收藏，两个请求几乎同时到达，两个都查到"还没有记录"，然后都插入——应用层的检查挡不住并发。只有唯一索引能让第二个请求失败（P2002），我们捕获它，转成"重复，不加分"。

**如果被问"怎么保证不重复加分"**：这是整个产品最容易被质疑的点，也是家长一眼能看出问题的地方（"我今天只看了 3 条，怎么加了 12 分"）。答案分三层：接口只调一次 `grant`、`grant` 里有唯一索引、索引冲突被转成静默的 `duplicate`。测试里有一条专门并发 10 次同一业务，断言只入账 1 条。

---

### 3.2 `balance_after` 是先插入再求和回填的

**做了什么**：事务里三步——写入流水（`balanceAfter` 先填 0）→ 对该用户求和 → 把求和结果 update 回这条记录。

**为什么**：直觉写法是"先查当前总分，加 delta，再插入"。但两个并发事务会读到同一个总分，各自算出同一个 `balanceAfter`，后写入的那条快照就是错的。插入之后再求和，拿到的是"包含自己这一笔"的真实值。

**如果被问"流水为什么要存余额"**：这是账本类系统的基本要求——每笔记录都带"这笔之后是多少"，对账时不用重算全部历史。真出问题时，一眼能定位到哪一笔开始不对。

---

### 3.3 日上限按求和算，不按次数算

**做了什么**：浏览类的今日得分 = `SUM(delta) WHERE biz_type IN (TERM_VIEW, ELEGANT_VIEW) AND createdAt >= 今天0点 AND delta > 0`，超过 20 分就拒绝。

**为什么**：现在词条和雅词都是 2 分，按次数算（10 次）和按分值算（20 分）结果一样。但万一以后改成"雅词 3 分、词条 2 分"，按次数算就错了。按金额算才是对的语义，而且不用改代码。

---

### 3.4 上限是"超额则不加"，不是"加剩余额度"

**做了什么**：如果 `今天已得 + 本次分值 > 20`，整笔不加，返回 `reason: 'daily_cap'`。

**为什么**：部分加会出现"浏览一条只加 1 分"这种奇怪的现象，用户看不懂规则。现在的规则一句话能说清：**每天浏览最多攒 20 分**。因为分值和上限都是 2 的倍数，不会浪费额度。

---

### 3.5 Prisma 把唯一约束冲突当 error 打日志，已过滤

**做了什么**：`lib/db.ts` 里改用事件方式接日志，遇到 `Unique constraint failed` 直接 return。

**为什么**：幂等冲突在设计上是**正常结果**，不是故障。不过在日志里它和真正的数据库错误长得一样，学生连点两下就刷一条红色 error，真出问题时会被淹没。

---

### 3.6 弱点（需要知道边界在哪）

**① 日上限依赖服务器时区。** `startOfToday()` 用的是 `setHours(0,0,0,0)`，即**运行机器的本地零点**。在自己电脑上是北京时间，没问题；如果哪天部署到 UTC 的云服务器，零点会偏移 8 小时，表现为"早上 8 点才重置"。真上线时要么在服务器上设 `TZ=Asia/Shanghai`，要么改成显式按 +08:00 计算。

**② SQLite 的并发写可能报 `database is locked`。** 现在并发量是"一个班几十人"，触发概率很低。如果真遇到，在 `.env` 的 `DATABASE_URL` 后面加 `?connection_limit=1` 让 Prisma 只用单连接排队，代价是查询串行，对这个规模完全够用。

**③ 积分只能加不能减。** 目前没有扣分场景（设计里也没有），所以 `grant` 只接受正数。如果以后要做"答错扣分"，需要另外想清楚扣到负数怎么办。

## 阶段 4 · 热梗辨析

### 4.1 浏览积分挂在详情接口里，不单独开一个加分接口

**做了什么**：`GET /api/terms/:id` 内部调 `grant(userId, 'TERM_VIEW', id)`，把结果放在响应的 `points` 字段里返回。前端拿到后 `usePoints().apply(d.points)`。

**为什么**：
- 少一次往返。拆成两个接口的话，前端要写"打开详情 → 成功后再调加分"，中间任何一步失败都会出现"看到内容了但没加分"或者"加分了但没看到内容"；
- 语义上"看过了"这件事就发生在打开详情的那一刻，不需要用户再做别的动作来确认。

**如果被问"GET 不应该有副作用"**：严格 REST 上确实不该。这是明确的取舍——副作用是**幂等**的（同一个词条一天只加一次分），重复请求不会产生额外效果，所以不会破坏 GET 的可重复调用性。代价是要接受"预加载详情会顺手加分"这种行为，本项目里没有预加载，不构成问题。

**为什么积分失败不能让详情崩**：整段包在 `try/catch` 里，出错只打日志。积分是附赠功能，不能因为它把一个孩子要看的内容页变成白屏。

---

### 4.2 详情用弹层，不新增 `/terms/:id` 路由

**做了什么**：点词条 → `TermDetailModal` 弹出并自己拉详情；关掉弹层，列表还在原位。

**为什么**：和第 2 阶段"登录不跳转"是同一个理由。列表页有搜索词、滚动位置、已加载的分页（41 条要翻 3 页），走路由跳转再返回，这些都要恢复。不跳转就根本不用恢复。

**代价**：详情页没有独立 URL，不能分享某一个词条。对这个产品（孩子自己看，不分享具体词条）可以接受；要分享时把 keyword 放 URL 查询参数比给每条词条建路由更划算。

---

### 4.3 收藏逻辑抽成一个 composable

**做了什么**：`web/src/composables/useFavorite.ts`，签名 `toggle(termId, current, apply)`。

**为什么**：列表卡片、详情弹层、雅词页、「我的」页四处都要"点了立刻变色 + 未登录先弹登录 + 失败回滚 + 加分飘字"。各写一遍必然出现三种行为——有的先变色再登录（未登录用户看到假的收藏态），有的失败不回滚（刷新才消失）。

`apply` 是个回调，由调用方决定"这个 id 的收藏态存在哪"：列表里是一条数组项，详情里是当前对象。组件不需要知道彼此的存储结构。

**乐观更新 + 回滚**：点击瞬间就变色，不等网络；请求失败则改回去并提示。这个产品里孩子手速比网络快，等 300ms 才变色的体验很差。

---

### 4.4 搜索防抖 300ms

**做了什么**：`watch(keyword)` + `setTimeout` 300ms，每次输入重置定时器。

**为什么**：不防抖的话，打一个"绝绝子"会发 5 个请求。更麻烦的是**响应顺序可能乱**——第一个请求慢、第三个快，列表最后显示的是第一个请求的结果，和输入框里的字对不上。300ms 是打字停顿的常见阈值。

---

### 4.5 搜索只匹配名称和释义，不匹配解析正文

**做了什么**：`OR: [{ name: contains }, { plainMeaning: contains }]`。

**为什么**：启发式解析是长文本（平均 78 字），参与匹配的话几乎每个词都能命中一堆不相关的结果。用户搜"绝绝子"要的是这个词本身，不是"某条解析里提到过绝绝子"。宁可少而准。

---

### 4.6 搜不到时的提示（数据边界，不是 bug）

**做了什么**：零结果时后端再查一次"雅词库里有没有这个词"，有就返回 `elegantHint`，前端显示"辨析页没有收录它的用法解析，但雅词库里有它的替换说法"+ 跳转按钮。

**为什么**：素材实测 41 条辨析 + 49 条雅词，只有 13 条重合。**「绝绝子」「yyds」「666」这些只在雅词页出现**，它们在 `term` 表里 `showInTerms=false`，释义和解析都是空串——硬塞进辨析列表会是一张空卡片。

孩子搜"绝绝子"看到"没找到"，会认为整个网站没有这个词，直接关掉。给一条路比给一句"没找到"有用。

**只在零结果时多查一次**，正常搜索路径上没有额外开销。

**v1.2 补充**：一开始只有"这个词在雅词库"时才给按钮。用户反馈"没找到那个按钮"——因为搜一个两边都没有的词（比如「火星文」）时，空状态就只剩一句"试试搜它的别称"，等于死路。现在**只要在搜索中，空状态必定有一个出口**：

| 情况 | 显示 |
|---|---|
| 雅词库有这个词 | 「去雅词积累」看「绝绝子」→（直达） |
| 两边都没有 | 「去雅词积累」搜「火星文」→（带词过去）+ 「不对，我要看全部词条」（清空搜索） |

只给一句"没找到"，孩子会以为整个网站没有这个词，然后关掉页面。

---

### 4.7 收藏一次给 1 分，取消不扣分，反复收藏不重复给分

**做了什么**：`POST /favorites` 里调 `grant(userId, 'FAVORITE', termId)`；`DELETE` 完全不碰积分。

**为什么**：积分只能加不能减（3.6 ③），扣分会导致负分和"我明明攒够了又变少了"的投诉。而"取消再收藏"能不能刷分，靠积分内核自己的幂等键 `(user, FAVORITE, termId)` 挡住——这是这类产品最常见的刷分漏洞，测试里有一条专门覆盖。

---

### 4.8 弱点

**① 搜索是 SQLite 的 `LIKE`，不分词、不支持拼音。** 搜"芭比q"能中（因为改写后的名字就是这个），搜"ba bi q"不中。要支持拼音得加一列拼音索引，现在不做。**中文场景下影响不大，因为关键词都短。**

**② 列表一次 20 条，没有虚拟滚动。** 41 条翻 3 页，够用。如果内容涨到几百条，要改成无限滚动或虚拟列表。

**③ 收藏列表接口做了，但页面在阶段 7。** `GET /api/favorites` 已经能用，现在只能通过接口看到。

---

### 4.9 这一阶段怎么验证的

- `npx tsx tools/smoke-stage4.ts`：**35 项断言**，真实 HTTP 打本地服务。覆盖分页不重不漏、搜索命中、精选取值稳定、浏览积分幂等、日上限、收藏幂等、取消不扣分、未登录拦截、总分与流水一致、每笔 `balanceAfter` 逐条累加一致。
- `node tools/shot.mjs <url> <宽> <高> <输出> [点击选择器] [自定义JS]`：无头 Chrome 截图 + **版面体检**（打印越界元素和 `scrollWidth`）。用它确认了 375/390px 下无横向溢出、PC 1280px 精选三列、弹层内容完整。
  - 需要登录态时给它 `YYXZ_TOKEN=<token>` 环境变量，脚本会预置 localStorage。

**这两件工具是这一阶段留下的资产**：后面每个模块都能直接跑一遍，不用手点。

### 4.10 弹层是可以叠加的，所以层级不能写死（bug 修复）

**问题**：未登录时在词条详情里点收藏，登录层弹出来了，但**被压在详情层下面**——用户得先关掉详情才看得见登录框。

**原因**：两层的 `AppModal` 都写死 `z-50`。同层级元素谁在上面，不取决于谁后打开，而取决于**谁在 DOM 里靠后**。两层都 Teleport 到 `body`，而 Teleport 的插入顺序按组件**挂载**顺序排——`LoginModal` 在 `App.vue` 里先挂载，`TermDetailModal` 在路由组件里后挂载，于是登录层永远在详情层前面，被压住。

**改法**：新增 `web/src/lib/modal-stack.ts`，弹层打开时"申请"一个位置：

| 机制 | 作用 |
|---|---|
| `zIndex = 40 + 栈深 × 10` | 谁后打开谁在上（详情 50、登录 60），不再依赖 DOM 顺序 |
| `isTop()` | 只有栈顶那层响应 Esc 和点遮罩。否则在详情里弹出登录框，按一次 Esc 会把两层一起关掉 |
| 滚动锁引用计数 | 两层都开时关掉一层，`body.overflow` 不该恢复——否则背景会跟着滚 |

**为什么不用一个更简单的写法**：给登录层写死 `z-[60]` 也能解决眼下这一处，但下次出现"三层"或者顺序反过来（登录先开、详情后开）就又错。栈是 O(1) 的复杂度，却把"叠放"这件事的规则写清楚了。

**怎么验证的**：`node tools/check-modal-stack.mjs`，不靠肉眼，直接量三件事——两层各自的 computed z-index、视口正中点 `elementFromPoint` 实际命中哪一层、按一次 Esc 后还剩几层。当前输出：详情 `50` / 登录 `60`，中心点命中登录层，Esc 后只剩详情且 `body.overflow` 仍是 `hidden`。

**顺带修的**：全局提示条 `ToastHost` 从 `z-[60]` 提到 `z-[90]`。否则弹层打开时的"已收藏"提示会被遮住——弹层里的操作反馈恰恰最需要看见。

**端到端复验**：`node tools/check-login-resume.mjs` 把整条链路走一遍——打开详情 → 点收藏 → 登录层出现 → 填手机号取验证码 → 登录 → 断言"登录层关闭、详情仍在、按钮变成 `★ 已收藏`、顶栏出现积分"。这条用例同时证明了 2.5 那个设计（`await requireLogin()` 挂住业务代码）在**两层弹层叠加**时依然成立。

### 4.11 详情里能收藏，列表里也能收藏，两处状态要同步

**做了什么**：`TermDetailModal` 收藏成功后 `emit('favorite-toggled')`，列表页 `setFavorite()` 同时改 `featured` 和 `list` 两个数组。

**为什么**：同一个词条可能同时出现在精选区和列表里（精选就是列表的前 10 条）。只改一处的话，用户在详情里收藏了，关掉弹层会看到精选区已变橙、列表里还是空心星——一眼就是 bug。

## 阶段 5 · 雅词积累

### 5.1 列表不返回对照词，展开才取

**做了什么**：`GET /api/elegant` 只回热梗名、通俗释义和"有 2 种更文雅的说法"这句提示；两条替换词及释义在展开时由 `GET /api/elegant/:termId` 返回。

**为什么**：两个理由，第二个更重要。

1. **首屏体积**：49 组、每组两段释义，一次塞 20 条进列表是 20×4 段长文本，手机首屏要等到明显卡一下。
2. **积分的语义**：浏览积分挂在"展开"这个动作上，才是"我真的读了这两条"。挂列表接口的话，翻页就能刷分——孩子不会真看，只会翻。这也和辨析页一致：**内容到达的那一刻才记分**。

代价：展开有一次 100ms 级的请求。折叠态有骨架屏，用户感知不到等待。已展开过的会缓存，收起再展开不重复请求、也不重复加分。

### 5.2 每日一句用"天数 % 总数"，不随机、不存状态

**做了什么**：`seq = (本地天序号 % 总条数) + 1`，同一天永远同一条，跨天自动换。

**为什么**：

- **不用随机**：随机的话用户刷新两次看到两句不同的，会觉得"这一句不重要"。固定一句才有"今天就是这句"的分量。
- **不存状态**：不需要一张"今天推过哪句"的表，也不需要每天跑定时任务。日期本身就是种子，重启、换机器、清库都不会错乱。

**踩到的坑**：第一版用 `Math.floor(Date.now() / 86400000)` 取天序号，那是 **UTC 天**——在中国时区意味着**早上 8 点才换句**，孩子 7 点打开看到的还是昨天那句。已改为减去 `getTimezoneOffset()` 的本地天序号。部署到 UTC 服务器时要设 `TZ=Asia/Shanghai`，这条和 3.6 的日上限是同一个坑。

### 5.3 雅词页的搜索要能搜到"雅词本身"

**做了什么**：搜索除了匹配热梗名，还匹配 `word1 / word2 / def1 / def2`（Prisma 关系过滤 `elegant: { is: { OR: [...] } }`）。

**为什么**：辨析页的入口是"我看到一个词不懂"，所以搜热梗名。雅词页的入口恰好相反——孩子记得「无与伦比」这个词很好，想找它对应哪个热梗、还能换成什么。只搜热梗名的话，「无与伦比」永远搜不到，而这恰恰是雅词页最典型的用法。

顺带：搜释义（如"找不出一点儿毛病"）也能命中，因为定义也进了匹配范围。

### 5.4 双向联动用 `?term=<id>` 深链，让弹层也能被跳转过来

**做了什么**：辨析详情原本是弹层、没有独立 URL（4.2 的取舍）。雅词页的"看它在什么场合不该用"要跳过去，于是约定 `/terms?term=<id>`：辨析页 `onMounted` 时读到就自动打开那张详情，**关掉弹层时把 `term` 参数抹掉**（否则刷新又弹一次，用户会以为关不掉）。

**为什么值得单独做**：这是全站唯一把"辨析"和"替换"接起来的地方——看到"什么时候不该用"，直接能翻到"该用什么"。数据上只有 13 条能命中（41 条辨析与 49 条雅词的重合数），其余 36 组展开时显示一句"辨析页暂未收录这个词的用法解析，这里只给替换说法"，**这是数据现状，不是程序漏了**。

同时做了反向的对称处理：两页的搜索词都写进地址栏（`?q=`），空状态互相跳转时带着词过去，不用用户重新输一遍。

### 5.5 每日一句放固定底栏，不放页尾

**做了什么**：`DailySentenceBar` 固定在底部，折叠态只露一句话，点开才显示出处与意义解读；`paddingBottom: env(safe-area-inset-bottom)` 避开 iPhone 底部横条。

**为什么**：放页尾的话，49 组要滑很久才看得到，等于没有。折叠默认是因为出处和解读是"老师会问的东西"，默认铺开会把正文挤掉——一句诗加解读能占大半屏。

**代价**：底栏会盖住页面最后一点内容，所以列表容器加了 `pb-20`。展开时最高 46vh，超出内部滚动。

### 5.6 弱点

**① 搜索仍是 `LIKE`，无分词、无拼音。** 搜"wu yu lun bi"不中。和辨析页同一个限制，中文短词场景影响不大。

**② 一次 20 条，无虚拟滚动。** 49 组三页到底，够用。

**③ 展开态不记忆。** 从雅词页跳去辨析再返回，折叠状态全丢。做的话要存 sessionStorage，收益不大，没做。

## 阶段 6 · 情景挑战

全项目最复杂的一块：抽题、判分、计时、结算，四件事每一件都能被作弊或被打断。这个阶段的取舍基本都是一句话：**能决定得分的东西一律放服务端，前端只管画和点**。

### 6.1 一轮 10 题，不是方案里写的 20

题库只有 23 题。抽 20 题意味着每轮只有 3 道题是新的，"再来一次"几乎还是那套题，抽题随机等于没做。定 10 题：23 选 10 每轮组合都不同，一轮约 2 分半，正好是课间能玩一次的时长。

改的是一个常量（`shared/point-rules.ts` 的 `QUIZ_SIZE`），抽题、判分、结算、前端进度条全都读它，没有别处硬编码。

**副作用（已知）**：正确率的分档门槛变成 10 的倍数，0/10/20/…/100，`≥90 / 70–89 / <70` 三档只剩 100、90、80、70 这几个落点。够用，但如果以后题库扩到 50 题以上，可以改回 20。

### 6.2 为什么要多一个 `/start` 接口（`served_at` 改成可空）

原计划是"建会话时给 10 道题统一写 `served_at = now()`"。写完发现这条路走不通：

> 服务端在 10:00 建会话，用户在 10:02 才点开第 5 题。这时 `now - served_at = 120 秒`，远超 16 秒阈值，**第 5 题一进来就判超时**。

问题的根子是：**服务端不知道用户什么时候点了「下一题」**。这个时刻只有前端知道，但前端的话不能信（否则改系统时间就无限答题）。

解法是把"前端报告时刻"变成"前端请求服务端记时刻"：

```
POST /sessions/:id/start { seq }  → 服务端此时才写 servedAt，返回 startedAt 与已流逝毫秒
```

- 前端进入某题时调一次，服务端用自己的时钟打点，前端仍然无法伪造时间；
- **只打一次**：重复调用返回最早那个时刻，不会重置倒计时。想靠"答到一半再 start 一次"续命是无效的（冒烟测试里有一条专门验证这点）；
- `served_at` 因此必须可空：null = 这题还没开始做。像原设计那样设 `@default(now())` 的话，10 道题在库里全都"已经开始了"。

多一次请求换来的是一句能站住的答辩话：**计时起点是服务端确认过用户已看到题目的那一刻**。

### 6.3 判分抽成纯函数，19 个单测

`server/src/services/quiz.ts` 里全是纯函数：`shuffle` / `toOriginalPick` / `toDisplayPick` / `judge` / `accuracyOf` / `tierOf` / `commentOf`。不连数据库，单测跑完 15 毫秒。

**为什么值得单独抽**：判分写反了，表现是"答对被判错"，孩子会觉得这网站乱判，而自己手测十次也未必撞上。这类 bug 靠人工走查发现不了，只能靠测试。

19 个用例里最关键的三条：

1. **交换后判对**：题库答案 B，这题左右换了，用户点屏幕 A → 判对，且库里存 `B`（原始位置）。
2. **阈值边界**：`elapsedMs = 16000` 判对，`16001` 判错。差 1 毫秒的 case 不写测试就一定会写错成 `>=`。
3. **超时就算点对也判错**：考的是限时反应，不是慢慢想。

### 6.4 屏幕上看到的 A/B 和题库里的 A/B 不是一回事

`display_swap = true` 表示这题这次左右换了：**屏幕 A 位放的其实是题库的 B**。

- 前端提交的是**屏幕位置**（用户点的是左边还是右边）；
- 服务端用 `displaySwap` 换算回题库位置再比；
- 库里 `chosen` 存**题库位置**，不是屏幕位置。

为什么存原始位置：将来要统计"这道题多数人掉进哪个坑"，用原始位置直接 `group by chosen` 就行；存屏幕位置的话每行都要再套一次 `display_swap` 才对，忘一次统计就是错的。

为什么不干脆把 `correctOption` 下发给前端自己判：那样答案就在浏览器的 Network 面板里，谁都能看。抽题接口的返回体里**一个答案字段都没有**（冒烟测试用正则扫过整个响应体）。

### 6.5 宽限 1 秒，但前端仍然显示 15 秒

`QUIZ_TIMEOUT_TOLERANCE = 1`：服务端判超时的阈值是 16 秒，前端倒计时显示 15 秒。

原因很实际：学生卡着最后一秒点，请求到服务端时已经 15.2 秒。不宽限就是冤案。那为什么不让前端也显示 16 秒？因为**显示和判定必须是同一个数**，否则眼尖的孩子会发现"倒计时完了还能点"。

代价是存在最多 1 秒的"超时后仍可答对"的窗口。这个窗口比"卡点被误判"的伤害小得多。

### 6.6 倒计时用重算，不用"每秒减一"

```ts
remainMs = questionStartedAt + seconds * 1000 - now   // now 由 100ms 的定时器刷新
```

不是 `spent++`。原因：手机切后台时浏览器会把定时器降到几十秒一次，减一法会**停在"还剩 12 秒"**，切回来还能慢悠悠想。重算法一回来就是 0。另外还监听 `visibilitychange` 主动刷新一次，不等定时器。

归零后由 `watch(expired)` 自动提交 `pick: null`，服务端判超时。**前端说了不算**：就算不提交，结算时那题也没答，照样算错。

### 6.7 反馈弹窗多给一句解析

方案里反馈弹窗只有三态文案 + 【下一题】。我在下面补了"正确答案 + 一句解析"。

理由：题库 23 条每题都带 `explanation` 字段，如果答完只告诉对错，这 23 段解析永远不会出现在界面上——那等于把内容白导入了一次。对小学生来说，"刚才那题为什么该选 B"比"你答错了"有用得多。

**风险**：答完立刻看到正确答案，同一台设备上第二个人玩就占了便宜。单机、单账号场景下可以接受，记录在案。

### 6.8 结算幂等 + `totalEarned` 从流水求和

`finish` 可以重复调用，因为结果页刷新会再调一次（结果页没有自己的查询接口，见 6.9）。

- 积分靠积分内核的 `UNIQUE(user_id, biz_type, biz_id)` 保证只发一次，`bizId` 就是 `sessionId`；
- `correctCount` 在第一次结算时写进会话，之后只读不算——万一将来有"改答案"，历史成绩也不该跟着变；
- **`totalEarned` 不用两次 `grant` 的 `delta` 相加**：第二次调用时两次都是 `duplicate`（delta 0），相加会显示"本轮 +0 分"，看起来像积分没到账。改成对 `point_record` 求和，任何时候调都是 15。

顺带一个坑：一题没答就点结算要拒绝（`answeredCount === 0` → 400），否则"开一轮再结算"就能白拿 10 分。

### 6.9 断线恢复不做，结果页刷新靠幂等的 `finish`

计划里就定了不做。理由是成本对比：`GET /sessions/:id` + 前端补状态 + 服务端补"进行中"分支，至少半天；而真实场景里"答题途中刷新"发生概率不高，出问题时用户重新开一轮也只需 2 分钟。

**但结果页刷新必须活下来**——点完"看结果"顺手刷新页面是很常见的手势。所以结果页的地址带 `?id=`，store 里没数据就用它再调一次 `finish`（幂等，不会重复发分）。这一步不额外加接口，是"结算幂等"顺带买到的能力。

答题页刷新则直接回 `/quiz`：`session` 在 pinia 里，刷新就没了。这是刻意接受的代价。

### 6.10 旧会话自动标 `abandoned`

开新轮时先 `updateMany({ userId, status: 'playing' } → 'abandoned'`。

不做的话，每次刷新页面都会留一条 `playing` 的僵尸会话，将来统计"闯关轮次"要额外过滤，而且永远不知道哪条是真的。作废之后 `finish` 会明确拒绝（"这一轮已作废"），不会出现"半路退出的轮次后来补发积分"。

**代价**：同一个人开两个标签页答题，先开的那个会被作废。单人产品，可以接受。

### 6.11 退出确认挂在路由守卫上

只拦自己的返回按钮等于没拦——右上导航的「首页」也能点。所以用 `onBeforeRouteLeave`：拦下导航、弹确认、确认后再 `router.push` 到原目标。

两个必须处理的细节：

1. 结算完成、用户确认退出，都要把 `allowLeave` 打开，否则跳转会被自己拦回来，卡死；
2. 拦截时要记住"原本要去哪"（`to.fullPath`），否则确认退出后只能回 `/quiz`，用户点「我的」却到了别的页。

### 6.12 弱点

**① 反馈里给了正确答案，同设备第二人可复用。** 见 6.7。

**② 断线恢复没有。** 刷新即重开，见 6.9。

**③ 判分是"位置对比"，不评估选项内容。** 题库里 `correctOption` 一改，历史统计会跟着变（`chosen` 存的是原始位置）。内容不打算改，接受。

**④ 并发重复提交可能双写。** 同一 `seq` 两个请求同时到达，都会通过"未作答"检查，后一次覆盖前一次。判分是确定性的，最坏情况只是 `answeredAt` 差几十毫秒，不影响积分（积分只认 `sessionId`）。没加行锁。

**⑤ 超时的 1 秒宽限可以被利用。** 见 6.5。

### 答辩问答（阶段 6）

**Q：答案存在数据库里，学生抓包能看到吗？**
不能。抽题、进入某题、提交答案三个接口的返回体里都没有 `correctOption`，只有"这道题对不对"和"该高亮哪个位置"。答案在服务端与用户提交的位置做比对后才产生结论。

**Q：改电脑时间能作弊吗？**
不能。前端传的任何时间都不参与判分，超时与否由服务端用 `served_at`（服务端自己打的点）和 `answered_at` 相减决定。

**Q：为什么答完就告诉正确答案，不是等全部答完？**
因为反馈的价值在于"刚犯的错立刻解释"，隔了 10 题再回看，小学生已经忘了自己为什么选那个。代价是同设备第二个人能复用答案，单账号场景可以接受。

**Q：一轮 10 题，23 道题够吗？**
够。23 选 10 每轮组合不同，5 轮之内重复率很低。题目不够时抽题会自动按实际数量开，不会硬凑重复题（`Math.min(QUIZ_SIZE, pool.length)`），所以以后题库增减都不用改代码。

## 阶段 7 · 我的界面 + 家校反馈

### 7.1 徽章定义写在代码里，库里只存"谁解锁了哪枚"

`shared/badges.ts` 里是 6 条 `{ code, name, description, icon }` 常量，数据库只有一张 `user_badge(user_id, badge_code, unlocked_at)`。

理由：徽章是**规则**，不是**数据**。如果做成后台可配置的表，就要有维护界面、要考虑"改了条件老用户怎么办"，而这份项目的徽章条件全写死在产品方案里。放代码里之后，将来换图标改名字只动一个文件，历史解锁记录完全不受影响。

判定函数 `evaluateBadges()` 自己保证幂等：先查已解锁集合，已解锁的直接跳过；写入用 `upsert`，并发也不会撞唯一键报错。

### 7.2 徽章是"事件触发"，不是定时任务

每次"可能让条件成立"的动作结束后调一次判定：查词条详情、展开雅词、收藏、闯关结算、打卡之后。6 枚全部拿到之后，这一步只剩**一次**查询（`pending.length === 0` 直接返回）。

如果做成定时任务（比如每小时扫一遍），会出现"昨晚该给的徽章今早才亮"——对一个给小学生用的产品，即时反馈就是全部意义。代价是每个写接口多 1–2 次查询；SQLite 单机下这是微秒级，不构成取舍。

### 7.3 打卡没有签到按钮 —— 它是"事后追认"

产品方案写的是"每日打卡 3 分，连续 7 天额外 20 分"。实现上**刻意没有做签到按钮**，判定条件是"今天有没有学习记录"：

```
有学习记录 → 打卡成立（查词条、展开雅词、完成闯关都会往 point_record 写一条）
只有打开首页 → 不成立（首页不产生任何积分流水）
```

原因很直接：做成一键签到，孩子会养成"每天点一下就关掉"的习惯，连续天数这个指标立刻失去意义——而连续天数正是家长报告里最有说服力的那一行。

配套的两个决定：

- **不建打卡表。** "今天有没有打卡"等价于"今天有没有 `DAILY_CHECKIN` 流水"，多建一张表就多一处可能和流水对不上的地方。
- **`bizId` 直接用日期键 `2026-11-16`。** 这就是"每天最多一次"的幂等键，不需要额外字段；连续奖励的 `bizId` 是 `2026-11-16#7`，所以第 7 天和第 14 天是两条不同流水，而"同一个第 7 天"重复调用仍然幂等。

### 7.4 收尾时发现的问题：打卡只在进站时触发，当天拿不到那 3 分

第一版把 `POST /api/checkin` 挂在"已登录"这个状态变化上（进站、登录后各一次）。走查时发现一个真实场景走不通：

> 孩子第一次打开网站 → 看了一个词条（+2 分）→ 直接关掉。**当天打卡的 3 分没发。**

因为打卡只在进站那一刻问过，那时"今天还没学"；学完之后没有再问。第二天再来时，"今天"已经变了，昨天那次打卡永远补不上——而连续天数本身是对的（它按 `point_record` 的日期算），于是出现"报告说连续 1 天、流水里却没有打卡分"的错位。

修法是把打卡抽成 `web/src/composables/useCheckin.ts` 里的一个幂等动作，在**四个地方**各调一次：进站/登录后、看完词条后、展开雅词后、闯关结算后。它自己做了三件事：

1. 记住已完成的日期键，当天成功后不再请求（否则翻十个词条就是十次无意义往返）；
2. `reason === 'no_activity'` 时**不记**，否则学完第一个词条就再也不会补分；
3. 全程静默失败——打卡是附赠，接口挂了不该让人以为网站坏了。

验证：新账号只点一个词条，总分应当是 **5**（浏览 2 + 打卡 3），实测就是 5，`streak = 1`。

### 7.5 连续天数做成纯函数，17 个单测

`server/src/services/streak.ts` 里 `getStreak()` 的输入只是"有学习记录的日期键集合"，输出一个数字。它最容易错在日期边界上，所以全部测掉：

- 今天还没学 → 昨天的连续不能断（**这条最容易写错**，写成"从今天往前数"就会把昨天的 6 天清零）
- 跨月（10-31 → 11-01）、跨年（12-31 → 01-01）
- 中间断一天 → 只算断点之后那一段
- 同一天多条流水 → 只算一天

日期键用**本地时区**生成，不用 UTC：中国时区下 UTC 差 8 小时，早上 8 点前会被算成前一天——这个坑阶段 5 的每日一句已经踩过一次。日期加减用 `Date.UTC` 做，避免时区偏移干扰。

### 7.6 `/mine` 与 `/report/summary` 共用同一个统计函数

两个页面显示的"查过多少词条、闯了几轮"必须完全一致。做法不是"两边各写一遍、小心保持同步"，而是 `getReportStats(userId)` 一个函数，`/mine` 和 `/report/summary` 都调它。

全部实时 `count`，不建聚合表：数据量是"一个孩子一学期的记录"，几千行以内；建聚合表就要处理"什么时候刷新"，那是纯负债。零记录时返回零值而不是 500——报告页要能显示引导，不能报错。

### 7.7 三段小结文案放在 `shared/`，不放在服务端

`shared/report-text.ts` 是纯字符串规则，不碰数据库。放 `shared` 的唯一目的是**能对它写单测**——验收要求是"任意数据组合都通顺"，这条只能穷举验证。

单测跑了 5×5×5×3×5×3 = **5625 种组合**，每条断言：三段都非空、不出现 `NaN/undefined/null`、不出现"0% 正确率很棒"这类硬伤、一句话里不出现两个句号（模板拼接错位会当场暴露）。

文案本身的三条写作约束（也是答辩要点）：

1. **家长视角**，说人话，不堆术语；
2. **不刺人**——数据差时不写"太差""需要加强"，写"下一步可以做什么"；
3. **不出现硬伤**——一轮没闯过时，任何一句都不许提正确率。

优势段宁可少一句也不写"你已经很棒了"这种空话；一段最多 3 句，多了家长不看，图也放不下。

### 7.8 没有内联中文字体，反而 `skipFonts: true`

方案里写的是"图片导出中文字体内联"，实际做下来**内联才是风险来源**：

内联要让 `html-to-image` 把字体转成 base64 塞进 SVG，一旦字体文件缺失或编码不对，导出的图就是方块字——而这正是方案里担心的那个失败。本站全站用系统字体栈（没有 `@font-face`），导出时浏览器用本机字体渲染中文，天然不会乱码，也不必为一张报告图多下载几百 KB。

代价：家长手机上没有的字体（艺术字）不会出现在图里——本站没用艺术字，代价为零。

另外两点：

- **`pixelRatio: 2`**：1x 的图在微信里一放就糊；
- **背景色写死 `#FAF7F2`**：不设的话圆角外的透明区在微信里会变成黑底；
- 被导出的那块卡片刻意用**纯白底 + Tailwind 类**，不引用外部图片和 CSS 变量——序列化成 SVG 时依赖越少越不容易失败。

### 7.9 导出按设备分流：桌面直接下载，手机才走分享面板

第一版写的是"能分享就分享，不能分享就下载"——判断依据是 `navigator.canShare({ files })`。上线走查时被当场抓住：**Windows 上的 Chrome 也支持带文件的 `navigator.share`**，桌面端点【保存为图片】弹出来的是一张系统分享面板，而用户的预期是文件落到「下载」文件夹。

修正后的规则：

```
桌面 / 笔记本      → 直接 a[download] 下载（不看 canShare）
手机 / 平板        → 优先 navigator.share；不支持或出错再退回下载
```

判断设备用 `navigator.userAgentData.mobile`（Chromium 系都有这个字段），老浏览器退回 UA 正则，iPadOS 13+ 的 UA 伪装成 Macintosh、用 `maxTouchPoints > 1` 认出来。

另外两个细节：

- **`a.click()` 之后不要立刻 `remove()`。** 一开始写的是"append → click → remove"，Chrome 会把还没写完的下载标成 canceled。游离节点上 `click()` 同样有效，所以干脆不插进文档。
- **分享面板被用户关掉（`AbortError`）不算失败**，不再补一个下载动作吓人。

文件名带日期：`雅言小筑-小雅士-20261116.png`，家长存下来一眼知道是哪天的。

验证方式（无头 Chrome + 埋点）：桌面环境点按钮后 `navigator.share` 调用 0 次、`a[download]` 触发 1 次（文件名正确）；模拟 Android UA 后反过来，share 1 次、download 0 次，提示语也相应变成"已打开分享面板，可存到相册"。

### 7.10 报告页的正确率在没闯关时显示"—"而不是 0%

`quizAvgAccuracy` 在没有闯关记录时是 0（后端方便计算），但界面上显示 0% 会被家长读成"一题都没对"。所以报告页单独处理：轮次为 0 时显示"—"，下面补一行灰字"还没闯过关，正确率暂不统计"。文案层也同步避开这个 0（见 7.7 第 3 条）。

### 7.11 弱点

**① 徽章判定分散在 5 个接口里。** 新增"可能解锁徽章"的动作时容易漏调 `evaluateBadges()`。没做成中间件是因为判定成本与"这次请求是否可能影响徽章"强相关，全局中间件会白白多查 5 次。接受：漏调的后果是徽章延迟到下次动作才亮，不会错发。

**② 打卡依赖"有积分流水"。** 如果某个学习动作将来不产生积分（比如"看每日一句"），它就不会被算作今天学过。目前四个动作都发分，暂时一致；`hasStudiedToday` 的注释里写明了这个前提。

**③ 图片导出只在 PC 无头 Chrome 上验过。** 真机 iOS Safari 的分享面板、中文字体渲染必须人工看一次（T7.5 标了 👤）。这是方案里 R5 风险的实际落点，不能算已通过。

**④ 报告数字实时算，没有缓存。** 每次打开报告页都是十来个 `count`。单用户几千行数据没问题，但这是"永远不建聚合表"这个决定的直接代价，写在这里免得以后误以为是遗漏。

**⑤ 昵称没有编辑入口。** 现在昵称是注册时随机的（"小雅士"这类），报告图上会带这个名字。要改就是加一个 `PATCH /api/me`，本期没做。

### 答辩问答（阶段 7）

**Q：打卡为什么没有签到按钮？没按钮怎么知道孩子打了卡？**
因为打卡的定义是"今天真的学了"，不是"点了一下"。判定条件是当天有没有学习流水——查词条、展开雅词、闯关都会写一条。做成一键签到，连续天数这个指标立刻变成"谁更闲"，家长报告里最有说服力的那一行就废了。副作用是它是"事后追认"的：孩子学完第一个词条，系统才回头把当天打卡分补上，所以界面上看不到任何"签到"动作，但分照发。

**Q：徽章条件是硬编码的，以后想加一枚要改代码？**
是，而且这是有意的。徽章是规则不是数据，六个条件都写在产品方案里，加一枚就是改 `shared/badges.ts` 加一行常量、在判定函数里加一个分支。如果做成后台可配置，就要额外处理"改了条件老用户算不算"、"配置错了怎么回滚"。这个项目的规模不需要那套东西。

**Q：报告图里的中文会不会变方块？**
PC 上验过不会。原因是全站用系统字体栈，导出时用本机字体渲染，没有字体文件要加载，也就没有"字体缺失变方块"的路径。反而方案里写的"内联字体"才是风险来源——base64 塞进 SVG，编码一错整张图就是方块。（真机仍需人工确认一次，见 7.11 ③。）

**Q：三段评语是模板拼的，会不会出现"孩子没闯关，评语说他正确率低"？**
不会。文案层第一条硬约束就是"一轮没闯过时任何一句都不许提正确率"，而且这条是用 5625 种数据组合穷举测出来的，不是靠人眼看两句。数据差的时候改写"下一步做什么"，不写"哪里不行"——这是给家长看的，措辞本身也是产品的一部分。

**Q：报告页的数字和「我的」页对不上怎么办？**
不可能对不上：两个接口调的是同一个 `getReportStats()`，不是两份实现。这是有意的结构设计，而不是"记得同步改两处"。

## 阶段 8 · 隐私同意、单端口生产模式、全站走查

### 8.1 监护人同意：前端是提示，服务端才是门

登录层原来写的是"登录即表示同意《隐私说明》"一行小字。面向未成年人收集手机号，这句话**等于没有取得同意**——它没有留下任何"用户主动做过一个动作"的证据。

改成必勾选项之后，真正的判断放在服务端：

```
POST /api/auth/sms/login { phone, code, agreed }
  ├─ 已存在且 consent_at 非空 → 老用户，不要求 agreed（不必反复同意）
  ├─ 新号码 / 早期账号未留痕 → agreed 必须为 true，否则 40000
  └─ 通过后把 consent_at 写成当前时间（留痕）
```

三个细节：

1. **顺序是"先判同意、后核销验证码"。** 反过来，用户忘勾选时验证码已经被消费掉，得等 60 秒重发才能再试一次——一个纯粹的界面失误变成了一次实际惩罚。
2. **勾选状态不记忆。** 记住"上次勾过"最省事，但对一个未成年人产品来说，"家长替孩子勾一次就永久生效"恰恰是最容易被质疑的地方。
3. **隐私页用新标签打开**（`target="_blank"`），不是路由跳转。否则用户点开说明再回来，手机号和验证码都空了。

### 8.2 隐私说明写到"能执行"的程度

一页隐私说明最容易写成三段正确但无用的话。这一版按六个问题分节，每条都给具体字段：

| 小节 | 具体到什么程度 |
|---|---|
| 收集什么 | 手机号（只用于登录与识别账号）、学习记录（词条/雅词/收藏/闯关成绩与用时）、同意时间；明确列出**不收集**位置、通讯录、相册 |
| 做什么用 | 登录、积分与徽章、生成家长小结图片、去标识化后的整体统计 |
| 不会做什么 | 不出售共享、不推广告、不向其他用户公开 |
| 存多久 | 账号存续期间；删除请求 7 个工作日内处理；验证码 5 分钟失效 |
| 监护人须知 | 明确"未满 14 周岁"、必须勾选才能登录、同意时间会被记录 |
| 权利与联系方式 | 查看/更正/删除三条路径 + 一个联系邮箱 |

最后一段还写明了"本项目为大学生创新创业训练计划项目，暂无商业运营，未接入广告或数据服务商"——这句话比任何免责条款都更能说明现状。

### 8.3 单端口生产模式：三处容易漏的细节

`npm run demo` = `build` + `start`，后端托管 `web/dist` 并做 history 回退。三个细节是实测才补上的：

**① 缺失的静态资源不能回落成 index.html。**
回退规则原本是 `/^\/(?!api).*/`，结果 `/assets/nope.js` 也返回 index.html（200 + HTML）。浏览器把 HTML 当 JS 解析，报的错跟真实原因完全无关，排查会绕很远。改成排除 `assets` 后，缺失资源老老实实 404。

**② `index.html` 必须 `no-store`。**
带 hash 的资源可以长缓存（`max-age=7d`），但 `index.html` 一旦被缓存，改完代码用户打开还是旧页面——"我改了怎么没生效"十有八九是这个。这一条是直接冲着踩过的坑加的。

**③ 二级页刷新不能 404。**
`/quiz/play`、`/report` 这些路径在服务器上并不存在对应文件，全靠回退到 `index.html` 交给 Vue Router。11 个路径逐个 `curl` 验证过全 200。

### 8.4 走查做成脚本，顺手抓出两个真问题

`tools/check-pages.mjs`：一个 Chrome 实例跑完 8 页 × 375 / 1440 两档，每页检查

- 横向溢出（`scrollWidth > clientWidth`）
- 控制台报错 / 异常 / 请求失败（白屏类问题的第一现场）
- 触控区高度 < 28px 的元素（手机上点不中）
- 固定底栏是否遮住正文最后一行
- 站内死链（收集所有 `a[href^="/"]` 后逐个 GET）

抓到的问题：

| 问题 | 位置 | 处理 |
|---|---|---|
| 「取消」按钮只有 24px 高 | `/mine` 收藏夹，5 处 | 改 `inline-flex h-9 items-center px-3` |
| 两个文字链接只有 16px 高 | `/mine`「去辨析页」、`/report`「去我的看徽章」 | `h-8` / `min-h-9` |

**脚本自己也会误报**：第一版报「/elegant 底栏遮住正文」，实际是长页面没滚到底就测量，最后一段还在视口外。修法是测之前先 `scrollTo(0, scrollHeight)`。这件事写在这里是想说明——自动化检查的结果也要先怀疑一下检查本身。

### 8.5 为什么最终不用 Docker，也不做端到端测试

| 放弃的 | 换来的 |
|---|---|
| Docker / Compose | 部署就是 `node` + 项目目录 + 一个 `.db`；出问题 `pm2 logs` 直接看，不用进容器 |
| MySQL / Redis | Prisma 换 provider 只改一行；本项目并发是"一个班几十人"，SQLite 足够 |
| Playwright E2E | 用 CDP 脚本做页面级走查（溢出/报错/触控/死链），覆盖"会真的坏"的部分，但不维护一整套测试环境 |
| 组件单测 | 只对**会算错且难排查**的两处写单测：积分幂等、判分计时；其余靠走查 |

判断标准只有一条：**这个投入能不能在答辩现场或真实使用中被感知到**。感知不到的工程化，对个人项目是负债。

### 答辩问答（阶段 8）

**Q：收集小学生手机号，合规上你们怎么处理的？**
三件事。一是所有字段在《隐私说明》里逐项列明，包括不收集什么；二是登录前必须由监护人主动勾选，勾选后才能建号；三是服务端把同意时间写进 `consent_at` 留痕，前端勾选只是提示，绕过前端也拿不到账号。此外提供了查看、更正、删除三条路径和联系方式。

**Q：为什么打卡没有签到按钮，连续天数怎么保证真实？**
打卡 = 当天有学习记录（查词条、展开雅词、闯关都会写一条流水），不是点一下按钮。做成一键签到，连续天数立刻变成"谁更闲"，家长报告里最有说服力的那一行就废了。

**Q：单端口部署有什么好处？**
一个 Node 进程同时提供接口和页面，没有跨域、不用配 Nginx 也能跑、`npm run demo` 一条命令就能起完整站点。前端是构建产物，缺失资源和二级页刷新这两件事在后端统一处理。

**Q：如果服务器挂了数据会丢吗？**
SQLite 是一个文件，手册里给了每日 3:10 的 cron 备份并保留 14 天，备份文件可以直接拷回本地用 DB Browser 打开验证。这是单机方案的代价，写进了已知风险。
